- **Why**: the owner, 2026-10-05: research tasks each re-derive what the routines and record fields
  they touch mean, and nothing they learn is written back into the code. `static/goal-exe/decompiled/`
  (T18, F009) still reads `f_0791_BBFF` and `*(undefined1 *)(iVar1 + 0x2d)`. A second view of the
  same code, with routine names, record types and global names, kept as tracked annotations and
  improved by every later task as it establishes a meaning, makes each question cheaper to answer
  and to review. Names are claims: each carries its basis and confidence, and starts `proposed`.

- **Scope**:
  1. **Annotations as tracked data** under `static/goal-exe/annotations/`: routines (address, name,
     one-line purpose, confidence, basis), record types (player, country: field offset, name, type,
     basis), globals (`DS:` offset, name, type, basis). Basis is a finding id, or decompiled/listing
     lines read for this row; confidence is one of a small fixed set (e.g. `established` for a
     finding's claim, `likely`, `guess`). A routine nobody has read keeps its `f_SSSS_OOOO` name and
     has no row.
  2. **A Ghidra step** that applies them (names, the two structs typed on the array pointers, global
     names and types) before decompiling, and a writer for `static/goal-exe/named/`, laid out as
     `decompiled/` is (per-segment files under the size limit, `index.tsv`), each heading keeping the
     listing address. `decompiled/` stays the raw, unannotated baseline of F009, unchanged.
  3. **A checker** `tools/static/check_annotations.py`: every row's address exists in
     `routines.tsv` or the data segment; names unique and valid C identifiers; confidence from the set;
     basis present and, for a finding id, an existing finding file; it prints coverage per segment
     (named / total).
  4. **A first pass of names**:
     - every routine and field the findings above establish, with its finding as basis;
     - the run-time library segments: each routine labelled by what it does (I/O, strings, sets,
       real arithmetic, …), as far as reading it shows, with confidence;
     - the direct callees of `0791:9564` and `0791:D733`, read and named, or left unnamed with no
       guess.
     Keep it practical: no name without having read the routine; "unknown" beats a guess dressed
     as a name.
  5. **The process**: `docs/process.md` §4's static-first line points to `named/` first, and a short
     section says each research task adds or corrects annotation rows for what it establishes (with
     its finding as basis) and regenerates `named/` in its PR. CLAUDE.md rule 22 names both views.
  Not in scope: answering backlog questions; changing any finding; editing `decompiled/`.

- **Hazards**:
  - names are claims: a name read from one routine without its callers is at most `likely`; mark a
    guess as a guess, and prefer no row to a wrong one;
  - Ghidra's struct typing on far pointers is a trust limit (F009): check a typed access against the
    listing before trusting it;
  - one Ghidra instance, two CPUs: the machine is shared (another task, T19, is in flight; never
    display `:99`; kill only your own processes);
  - keep each shell command under 5 minutes or run it in the background; the full decompile takes
    a while.
