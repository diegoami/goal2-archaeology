# T44 The recorder keeps one save in flight and merges the key groups that settle while it writes

- **Kind**: tool fix (the recorder, `runtime/human/`), from issue #128
- **Issue**: #128 · **Branch**: `task/T44-one-save-in-flight` · **Merge after**: —
- **Implementer**: the `implementer` subagent on sonnet · **Reviewer**: luna (the owner's standing
  choice for this session, 2026-10-12)
- **Why**: the owner's first sitting on the new machine (20261011-161003, 10.5 min) sent 537 save
  requests and **313 were superseded** (58%: nothing staged). They cluster in menu and formation
  screens, where the owner scrolls with Up/Down held (auto-repeat, 85 presses within 0.1 s of the same
  key). The median gap between requests was 0.15 s, shorter than one DOSBox-X save (about 0.8 s,
  about 53 write events), so later saves overwrote earlier ones and T35's ownership guard refused to
  stage them. The coaching kit's live view goes blind exactly where the owner scrolls.
- **The owner's decision** (2026-10-12): the fix is wanted; the merge rule is the main session's
  proposal (option A): the snapshot of a merged request is claimed as the screen after the LAST key of
  the merged groups, and the screens after the earlier groups are recorded as not captured, never
  attributed.
- **Protects**: the record's integrity (T35): every staged snapshot is owned by exactly one request whose
  write it proves (the per-request path, `pre_sig`, the write-event count); no key is lost or invented;
  the live savestate is never staged mid-write; a pause still sends nothing (T39b).
- **Evidence** (pasted):
  - `runtime/human/recorder.py` `Watcher.run` (lines ~1344-1517): each settled key group's request goes
    out `EVENT_SETTLE_S` (0.05 s) after its newest key event (`send_burst`), whatever is in flight; the
    capture runs in the `capture-pipeline` worker (`submit` -> `_stage_job`), counted by `_submitted`
    and `_finished`. `Burst` (~255-283) keeps one group per settled episode: "N groups produce N burst
    snapshots, one per loop pass"; `consume()` pops the head group, and the send records
    `request_time`/`sent` on it (the window the map reads).
  - A superseded request: `_stage_job` raises `_AttributionLost` when a later save overwrote this one's
    before it was read; `note_request(..., superseded=True)` writes the line, nothing is staged.
  - The recorder self-invariants in `experiments/E015-human-playthrough/scripted_keys.py`:
    `check_bursts`, `check_request_windows`, `check_attribution`, `check_mapped`; a scripted sitting runs
    the real DOSBox-X on private displays (`--keys`, `--gap-min`, `--gap-max`, `--seed`).
  - `docs/recorder-architecture.md` describes the pipeline and the guards; tests in
    `tests/test_human_record.py`, `test_human_pause.py`, `test_human_keys.py`, `test_human_resume.py`.
- **Owns**: `runtime/human/recorder.py`, `experiments/E015-human-playthrough/scripted_keys.py` (the
  checks, for merged groups), `experiments/E015-human-playthrough/extract.py` and the key/screen map code
  it uses (only for merged groups), `tests/test_human_*.py`, `docs/recorder-architecture.md`, new
  rehearsal logs `experiments/E015-human-playthrough/T44-*.log`
- **Scope**:
  1. At most one save request in flight: no burst, cadence or resume request is sent while the previous
     request's capture has not finished (staged, superseded, or its deadline passed). Cite where
     "finished" is read.
  2. Key groups that settle while a request is in flight wait; when it finishes, ONE request is sent for
     all of them. Each merged group records the shared `request_time`/`sent` and a marker naming the
     merge (its size and position), so the map can tell a merged group from a lone one.
  3. The map and the checks follow option A: one snapshot per merged request, claimed for the last group;
     the earlier groups of the merge are listed as "not captured" with their keys; nothing else of the
     T35/T39b guarantees changes. A cadence tick due while a request is in flight is sent after it, not
     dropped and not doubled.
  4. `docs/recorder-architecture.md` describes the rule.
