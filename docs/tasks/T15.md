# T15 Q004: where and how are player skills and attributes made? (G5 Q004)

- **Kind**: research (behavioural and static)
- **Issue**: #43 · **Branch**: `task/T15-q004-skills` · **Merge after**: T12, T13
- **Implementer**: the main session or a scoped helper using caller-configured model/settings; no fixed model or automatic per-task spawning. See [model policy](../model-policy.md).
- **Reviewer**: independent under the repository review rules; caller-configured model/settings, without a named-model requirement.
- **Why**: `GOAL.DAT` holds no player skills (F002 R013), yet the rebuild's start state and every
  skill question (Q005, Q009–Q012) need to know how each player's values come to be, and whether a
  new game's seed changes them.
- **Evidence** (pasted):
  - `docs/backlog.md` Q004: *Skills are drawn when a game starts: two new games with different
    seeds give the same names but different skills; the draw is scaled by a per-country value
    (R007 or R008), so mean skill follows country strength.* Static route: `1771:97CC` (creates a
    country's 20 players, reads `DS:A978`) and `1771:96D3`; the 20-byte record at `[A91B]` and its
    fields; `1771:9A40` copies R008 into field +0x2D of the country record.
  - F002 / `static/goal-exe-map.md`:
    - the player record is 20 bytes, 3061 of them, at the far pointer `[A91B]` (0xEF24 bytes,
      allocated by `2139:0000`);
    - `1771:9B85` starts a new game and calls `1771:9A40`;
    - `1771:9A40` builds the 128 country records (0xBF bytes at `[A917]`), copies block 7
      (`DS:9B7C`, R008: one byte per country, 34 values from 54 to 254) into field +0x2D, and calls
      `1771:97CC(country)`;
    - `1771:97CC` calls `1771:96D3` for slots 1..20 with the player number, the country, a byte of
      block 10 (`DS:9F03`, the position) and 1;
    - `1771:377E` reads fields +4, +0xC and +0xE ("a player's value", inferred);
    - `0791:BC5D` copies the position byte into field +6;
    - R007 is block 6: three bytes per country, each 9..15, read by `0791:1073`.
  - F004: the RNG `214B:0688` (16-bit LCG, `seed*0x7ABD+0x1B0F`, 1..n) seeds `DS:7B62` from the DOS
    hour:minute when a new game starts. The driver sets the DOS date and time (`--dos-time`,
    `--dos-date`, I3). The data segment's linear base is found per savestate
    (`runtime/driver/savestate.py`, `find_program`; DS 2DA4, linear 0x2DA40 in every record so
    far). A far pointer such as `[A91B]` is read from DS and then followed in guest memory.
  - F001's keys to the main screen (`n Enter Enter b o b Enter Enter Enter Enter`) start a new game
    as the country they pick; E004's `run.py make-state` reaches the main screen at a set DOS time.
  - T13: `tools/publish_evidence.py E<nnn> --run <id> --file <path>` publishes a start state to the
    experiment's release.
- **Owns**: `experiments/E006-*/**`, `runs/E006/**`, `findings/F007-*`, `evidence/E006/**`,
  `runtime/driver/**` (additions only), `tests/test_driver*.py`, `runtime/README.md`
- **Scope**: protects the claim that the rebuild can set every player's values as the original
  does at a new game (or the claim that they depend on inputs it must reproduce). Behavioural: from
  new games at fixed DOS times, read the whole player array at `[A91B]` (and the country records at
  `[A917]`) from a savestate at the main screen. Compare games across DOS minutes and within one
  minute, field by field. Then relate each country's player values to R007 and R008. Static: what
  `1771:96D3` writes into each field of the 20-byte record, from which inputs (the RNG draws and
  their ranges, the position byte, the country's values), and when it runs (start-up, new game, or
  both). Not in scope: what each skill does in a match (Q010–Q012); how the screen shows them (Q009);
  ageing and form over a career (Q013–Q016).
- **Done when**:
  1. `python3 tools/validate_runs.py runs/E006` passes; every record that sets the clock declares I3.
  2. At least 10 new games at distinct DOS minutes and 2 at one repeated minute are in `runs/E006/`.
     `python3 experiments/E006-*/summarise.py` prints, per field of the 20-byte record:
     - whether it differs across minutes and whether it is equal within a minute;
     - its range over all 3061 players;
     - for a varying field, how its per-country mean relates to R007 (each of its three bytes) and
       R008: a correlation or a fitted line, with n = 128.
  3. `findings/F007-*.md` (`proposed`) answers Q004. Each claim has a behavioural citation (run ids)
     and a static citation (listing lines); nothing is `corroborated` from one route. Each field is
     named with what writes it, from which inputs, and with what range, or "not established". Each
     claim is worded with its confidence: the owner accepts a claim about 80–90% likely when the
     wording says so.
  4. The start states the records name are published with `tools/publish_evidence.py E006`, and
     `python3 tools/verify_evidence.py E006` passes.
  5. `python3 -m unittest discover -s tests` and `discover -s tests/static` pass. Each new check
     (in particular any parser of the player or country records) has a test that fails when its
     offset or size changes by one; T07's Done-when 7 command prints nothing.
- **Hazards**:
  - L207: commit and push records after each batch and at least every 30 min; never delete or
    overwrite;
  - a far pointer read wrong: verify the player array's location on a known value (e.g. a player
    number in the country record's first 20 words, or the 3061 × 20 size) before reading fields;
  - a shared machine: never display `:99`; kill only process groups the driver started;
  - concluding beyond the runs: "drawn at new game" needs both routes; a field equal in every game
    may still be drawn from a fixed seed at start-up, so say which;
  - keep it practical: no more runs than the claims need.
