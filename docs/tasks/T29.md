# T29 recorder: the owner's playthrough as a complete behavioural record

- **Kind**: tooling + research (a recorder around a human playthrough; static still rules what the
  recordings corroborate)
- **Issue**: opened at dispatch · **Branch**: `task/T29-human-playthrough` · **Merge after**: T28
- **Implementer**: the main session or a scoped helper using caller-configured model/settings; no fixed model or automatic per-task spawning. See [model policy](../model-policy.md).
- **Reviewer**: independent under the repository review rules; caller-configured model/settings, without a named-model requirement.
- **Why**: the owner plays the game and hands over recordings and saves; one playthrough must
  yield every fact the project needs, not one scenario per fact (the owner, 2026-10-07). A
  savestate is the whole machine state, so a timestamped chain of them plus a screen video is a
  complete behavioural record any later question can be mined from without new play.

- **Hazards**:
  - never send emulator hotkeys to any window but the emulator the recorder launched — the
    owner's terminal would receive them; the window gate is a correctness rule, not a convenience.
    The gate is window identity, not focus: WSLg's XWayland exposes no focus API
    (`xdotool getactivewindow` and `getwindowfocus` both fail, 2026-10-07), so the key goes by
    `xdotool key --window <wid>` to the wid whose pid is the launched DOSBox-X, failing closed
    when no window binds to that pid;
  - the watcher never renames, moves or writes the savestate DOSBox-X is writing: it opens the
    live file read-only, and never stages bytes read while a write was in progress (a write
    session open before, during or after the reads rejects them), so every staged copy is a
    complete savestate. A read-only open cannot disturb the writer; no reader can promise a
    write never begins during its read without the writer's cooperation, which DOSBox-X does
    not offer (no locks), so the guarantee is on what is staged (the owner, 2026-10-08,
    option 1 of T29's round-6 escalation, correcting ca10276's "never reads it").
    The writer model is single-writer: each sitting's session folder is private to the recorder,
    and the DOSBox-X process the recorder launched is the only writer of its live savestate
    (one write session per save). A second, overlapping writer of that file is outside this
    task: no unprivileged mechanism here can count another process's write descriptors
    (inotify reports no open mode; fanotify needs root; /usr/bin/dosbox-x's cap_net_raw makes
    its /proc/<pid>/fd unreadable). The owner chose this scope, option 1 of T29's round-5
    escalation (2026-10-08);
  - savestates and videos stay out of git (rule 18's family): only records, hashes and
    extracted text are committed;
  - the owner's sitting is not scripted: the extraction must tolerate arbitrary screens,
    restores, pauses and a mid-session stop; a partial chain still produces a valid record;
  - GOAL2's own saves (if the owner saves in-game) land in the mounted game dir — mount a
    per-session copy, never the release cache (F001: a savestate remembers the mount).
