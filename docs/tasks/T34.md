# T34 recorder 2: the keys typed into the game, and the screen/key map they draw

- **Kind**: tooling + research (extends T29's recorder; the map it extracts corroborates static key
  handlers)
- **Issue**: #105 · **Branch**: `task/T34-game-keys` · **Merge after**: T29
- **Implementer**: claude (`opus`), from rework round 1 (2026-10-09): the Claude Opus review was

  R2: the map does not check its brackets are adjacent; R3: the privacy test cannot fail —
  xdotool --window makes no raw events; R4: --video cannot find the Xephyr window), so the round

- **Reviewer**: round 1 claude (`opus`) on Sol's code; from rework round 1 `gpt-6.1-sol` (delta
  review) on the Claude-written delta: each part reviewed by the other family
- **Why**: the owner's direction (2026-10-09): the recorder sees the game's screens every 20 s but
  not what moved it from one screen to the next. Which keys work on which screen (C skips the
  corner/penalty taker selection, N skips replays, Ins takes the assistant's 20) is what the
  automated sessions lacked when they got stuck (T28's E014 stall at EA09), and what a rebuild of
  the game's screen flow needs. Static analysis finds key handlers one by one; the owner's play
  shows which keys matter, on which screens, in which order.
- **Evidence** (pasted):
  - T29 (merged a7aa551): `runtime/human/play.sh` + `recorder.py` run windowed DOSBox-X, stage a
    savestate every 20 s (keys to the launched window only, by pid; inotify write-session gate;
    single writer), optional video; `experiments/E015-human-playthrough/extract.py` turns a session
    into a run/1 record (screens, the [A923] state, records, diffs).
  - The owner's question (2026-10-09): the recorder does not log keys, so the per-screen key
    knowledge is lost. Design agreed with the owner: DOSBox-X runs inside a nested X server
    (Xephyr) shown as an ordinary window; a key logger attached to THAT display only sees the keys
    typed into the game. Other programs are not on that display, so they cannot be captured — a
    structural guarantee, not a filter. The owner installs `xserver-xephyr` and `xinput`.
  - The G1 driver reads the text screen from savestates (`runtime/driver/savestate.py`), so a
    screen is identified offline by its text.
  - T28 E014 notes §7-8: the stuck screen (EA09's silent refusal of an ineligible player; the
    recovery Space → Ins → Esc), an example of a screen/key fact the map should capture.
- **Owns**: `runtime/human/**`, `experiments/E015-human-playthrough/**`, `runs/E015/**` (new
  records only), `evidence/E015/**`, `tests/test_human_record.py`, `tests/test_human_keys.py`,
  `runtime/README.md`
- **Scope**: in steps that each end in a pushed commit (L103):
  1. The nested display: `play.sh` starts Xephyr (a free display number other than `:99`, window
     sized from `--res`), runs DOSBox-X on it, and keeps T29's behaviour (snapshots, the gate,
     video of the Xephyr window). `--self-test` checks Xephyr and xinput exist.
  2. The key log: a logger attached to the nested display only (XInput2 raw/key events or the
     RECORD extension on that display) writes each key event — wall time, monotonic time,
     press/release, keysym and keycode — to the session's `keys.jsonl`, flushed per line. No
     global hook, never the owner's main display.
  3. Snapshots on keys: besides the 20 s cadence, one snapshot shortly after each burst of keys
     (a quiet interval after the last key, its value [designed] with the search said), through the
     same capture gate, so each key has a screen before and after.
  4. The screen/key map: `experiments/E015-human-playthrough/keymap.py` reads a session (snapshots,
     index, keys.jsonl) and emits, per screen (identified by a digest of its text, with a readable
     headline), the keys pressed on it and the screen each led to, with counts; written into the
     session's run/1 record and as a readable table under the experiment. The protocol's coverage
     map gains the rows it fills.
  5. Tests: the logger sees keys sent to the nested display and NOT keys sent to another display
     (a second Xvfb standing in for the owner's desktop); the burst-snapshot timing; the map from a
     literal fixture session (snapshots + keys) to a literal expected map.
  Not in scope: replaying a session's keys into the game (a later task); the bot.
- **Done when**:
  1. `bash runtime/human/play.sh --self-test` checks Xephyr, xinput (or the logger's dependency),
     dosbox-x and the release; a scripted sitting on private displays (a Xephyr nested in an Xvfb
     standing in for the owner's desktop; keys sent with xdotool to the game, and other keys sent
     with `xdotool key --window <id>` to a second application window on the outer display, e.g. xev)
     yields a session whose `keys.jsonl` holds every key sent to the game and none sent to the other
     application, and
     whose index holds a burst snapshot after each key burst; `python3 tools/validate_runs.py
     runs/E015` passes on its record.
  2. `python3 experiments/E015-human-playthrough/keymap.py <session>` prints the map's summary
     (`screens: N, transitions: M, keys: K`) and the run/1 record carries it; it is right on a
     literal fixture (tests).
  3. `python3 -m unittest -v tests.test_human_keys tests.test_human_record` passes, and removing
     the display restriction, the burst snapshot or a map rule makes at least one test fail (the PR
     lists the mutations run, in place).
  4. `python3 -m unittest discover -s tests` and `discover -s tests/static` pass (the
     test_driver_e008 host-path test under an in-worktree TMPDIR is the main session's line,
     #100); `python3 tools/check_links.py` passes.
- **Hazards**:
  - privacy is the correctness rule here: the logger attaches only to the nested display it
    started; a key typed into any other application is never read. A test proves it with a second
    application window on the outer display. Mind the probe of 2026-10-09: a key sent to the outer
    display while the Xephyr window holds the focus IS game input (Xephyr forwards it) — that is
    the owner typing into the game, not a leak; the test must target another app's window (in the
    probe, `xinput test-xi2 --root` on the nested display saw only the game's a/b, and an xev window
    on the outer display received x/y/z);
  - T29's gates stay: keys only to the launched window, the live savestate never staged while a
    write is open, single writer, records immutable;
  - keys.jsonl and savestates stay out of git (scratch/human/sessions/, git-ignored); the committed
    record carries the map and hashes, and the keys of the scripted sitting only;
  - never display `:99` (another project uses it); kill only your own processes, by pid;
  - long commands run detached with a log, polled in short calls; push after each step and at least
    every 20 minutes; open a draft PR after the first push.
