# T18 Decompile GOAL.EXE with Ghidra: pseudo-C per routine, checked against the listing (G3)

- **Kind**: static (tooling and a derived extract)
- **Issue**: #52 · **Branch**: `task/T18-ghidra-decompile` · **Merge after**: T04
- **Implementer**: the main session or a scoped helper using caller-configured model/settings; no fixed model or automatic per-task spawning. See [model policy](../model-policy.md).
- **Reviewer**: independent under the repository review rules; caller-configured model/settings, without a named-model requirement.
- **Why**: every static claim so far (F002, F004–F007) was read by hand from capstone's assembly in
  `static/goal-exe/code/`. The match engine (`0791:9564`, `0791:D733`), which decides results and so
  matters most for the bot, is thousands of instructions long. Pseudo-C per routine would let the
  engine's rules (Q010–Q012, Q027 and others) be read nearly directly, with behavioural runs then
  confirming specific predictions. F002 named Ghidra as the missing static tool.
- **Evidence** (pasted):
  - `static/goal-exe/README.md`:
    - the listing is generated from the released `GOAL.EXE` (set `goal2-a949da2f`, packed sha256
      `a6928b0b…`, LZEXE 0.91), unpacked by `tools/static/unlzexe.py` (sha256 `6fd8c5ef…`, 193408
      bytes, never committed);
    - addresses are `SEGMENT:OFFSET`, SEGMENT being the paragraph in the image before relocation;
    - the image offset is SEGMENT×16 + OFFSET; the file offset adds the 8192-byte header;
    - data segment 2581; entry 0000:0000;
    - 57508 instructions, 142044 of 153616 code bytes decoded; the rest reported as data.
  - `static/goal-exe/routines.tsv` (every routine found), `calls.tsv`, `datarefs.tsv`,
    `strings.tsv`; `tools/static/regenerate.sh` rebuilds them.
  - Installed by the main session (2026-10-05), outside the repository: Ghidra 12.1.4
    (`~/tools/ghidra_12.1.4_PUBLIC`, release `Ghidra_12.1.4_build`) and Temurin JDK 21.0.12.1
    (`~/tools/jdk-21.0.12.1+1`). `support/analyzeHeadless` runs with `JAVA_HOME` set to that JDK.
    Ghidra's x86 processor and its MZ (old-style DOS) loader are included.
  - Hand-traced claims to check the output against (all reviewed):
    - F005: `0791:97D0` calls `0791:D733` when `DS:9A3E` is set, else `0791:9564`; `0791:A4A1` is the
      per-match set-up;
    - F007: `1771:97CC` writes the country number into `DS:7B62` before calling `1771:96D3`;
      `1771:10E7` is `((5 − [+0x2C]) · (0x21 − [+0x2A]) + (0x81 − [+0x2B])) idiv 2`; `1771:32EB`
      computes +4 from +1, +2, +3;
    - F004: `214B:0688` is the LCG `seed·0x7ABD + 0x1B0F`, returning 1..n; `214B:1DA7` calibrates a
      delay into `DS:A9FF`.
- **Owns**: `tools/static/decompile.sh` and `tools/static/ghidra/**` (new), `static/goal-exe/decompiled/**`
  (new), `findings/F009-*`, `tests/static/test_decompile*.py`, `static/goal-exe/README.md` (one
  paragraph pointing to the decompiled view), `docs/environment.md` (the Ghidra and JDK lines)
- **Scope**: protects the claim that the decompiled view says what the code does, so that later
  tasks may read it in place of the assembly; where it does not, it says so.
  - **The tool:** `tools/static/decompile.sh <released GOAL.EXE> static/goal-exe/decompiled`. It
    unpacks with `tools/static/unlzexe.py`, checks the unpacked sha256, and loads the file in Ghidra
    headless (MZ loader, x86 real mode) with the segments placed so that each function's address
    matches the listing's `SEGMENT:OFFSET`, or with a stated, tested mapping. Every routine in
    `routines.tsv` becomes a function. The tool runs Ghidra's analysis, decompiles each function,
    and writes it. Ghidra and the JDK come from `GHIDRA_HOME` and `JAVA_HOME`; the versions are
    checked and written into the output's README.
  - **The output:** pseudo-C per code segment, split into files under about 20k tokens (rule 16),
    each function headed by its listing address. An `index.tsv` gives, per routine in
    `routines.tsv`, its file and line, or why it failed to decompile. Data-segment references show
    as `DS:XXXX` where Ghidra can resolve them.
  - Not in scope: renaming or retyping by hand beyond what the scripts do; any behavioural run;
    editing the capstone listing.
- **Done when**:
  1. `bash tools/static/decompile.sh <GOAL.EXE from the release> /tmp/out` run twice gives
     byte-identical output, and that output equals the committed `static/goal-exe/decompiled/` (the
     PR pastes `diff -r` printing nothing).
  2. `index.tsv` covers every routine of `routines.tsv`. The PR pastes the counts: decompiled,
     failed (with reasons), and any Ghidra function not in `routines.tsv`.
  3. `findings/F009-*.md` (`proposed`, static route only) has a table, one row per hand-traced claim
     under Evidence. Each row gives the claim, the decompiled lines that show it (or contradict it),
     and agree / disagree / unclear. At least 9 of the 10 claims are checked. It states what the
     decompiled view can be trusted for and what it cannot (for example far pointers, segment
     arithmetic, Pascal strings and sets).
  4. `python3 -m unittest discover -s tests/static` passes, with a test that the address mapping
     puts at least three known routines (e.g. `0791:97D0`, `1771:97CC`, `214B:0688`) at their listing
     addresses. The test is skipped with a stated reason where Ghidra is not installed (CI).
  5. No original or unpacked file is tracked (T07's Done-when 7 command prints nothing); no file this
     PR adds or changes is over 1 MB (run records already on main are exempt, as the owner allowed in
     T12); `python3 tools/check_links.py` passes.
- **Hazards**:
  - segment numbering: Ghidra's MZ loader relocates to a base segment of its own; get the mapping
    to the listing's numbers right and test it, or every later citation is wrong;
  - non-determinism: Ghidra's output can vary with analysis order or version; pin the version and
    the options, and prove the output is reproducible;
  - a decompiler's confident wrong output: the check against hand-traced claims is the point of
    F009, so do not tune the scripts until the table agrees;
  - the shared machine: Ghidra is memory-hungry; keep `-max-cpu` modest and run one instance.
