# Research backlog (G5)

The questions research has to answer before the spec covers what the rebuild and the bot need
(G-M3 of [plan.md](plan.md)). Each row says how it would be answered on both routes, behavioural and
static (U16): `corroborated` needs both. A question becomes a task when it is scheduled; its status
lives in that task's issue, never here.

## How to read a row

- **ID**: `Q001…`, stable. Rows are ordered by what G-M3 needs: first the questions every
  behavioural measurement depends on (Q001–Q004), then the areas the match touches, then the rest.
- **Area**: the knowledge-map row ([knowledge-map.md](../knowledge-map.md)); the help file's
  candidate question it refines, as `Qaa.n` of [sources/goal-hlp.md](../sources/goal-hlp.md).
- **Prediction**: what is observed if the claim holds, so that a run can contradict it. `GOAL.HLP`
  lines are cited where the help file makes the claim.
- **Behavioural**: what to run under the G1 driver (T07), with the sample size. *Seeded* means after
  Q001 gives a way to fix the random input (an I3 intervention, declared). *Savestate* means a
  memory read from a savestate (I1).
- **Static**: where to read in the unpacked `GOAL.EXE`. An address `SSSS:OOOO` is a routine of
  [static/goal-exe/routines.tsv](../static/goal-exe/routines.tsv); `DS:OOOO` is in the data segment.
  *Not placed* means F002's map ties no routine to the area, and the cell says where to search.
- **Unblocks**: what an answer makes possible: a rule of the rebuild (`goal2`), the bot, or another
  question.
- **Difficulty**: the routing class of game-archaeologist `docs/models.md`. Rules, formulas or
  constants from evidence are **hard**; observation and transcription are **easy**.

## Leads from the listing (not findings)

Read while writing this backlog, from the listing of T04 (basis `static:listing`, not reviewed).
They shape the static routes of Q001–Q004 and are to be confirmed by those questions' findings.

- `214B:0688` is a 16-bit linear congruential step: it loads the word at a far pointer, multiplies by
  `0x7ABD`, adds `0x1B0F`, stores it back, and returns the high word of the product with its
  argument `n`, plus 1 (a value in 1..n). `214B:06B1` calls it with the pointer at `DS:A978` and an
  argument `n` (61 callers: 18 in `000E`, 32 in `0791`, 11 in `1771`); `214B:06D0` returns whether
  that value is 1 (17 callers); `214B:06FA` does so with `n` = 2 (33 callers).
- `214B:206A` (that unit's start-up) stores the far pointer `DS:7B62` at `DS:A978`.
- `23E4:11D7` calls INT 21h AH=2Ch (get time) and stores CX (hour, minute) at `DS:7B62` and DX
  (second, hundredths) at `DS:7B64`: the run-time library's seeding from the clock. Its only caller
  is `1771:6730`, whose only caller is `1771:76B1`. `1771:76B1` calls `1771:6730` only when the byte
  at `[A923]+0x3C` is 2 or 5 (the codes `1771:580B` names "qualifying"), and has two callers: the main
  program (`0000:0000`), once before the screens, and `000E:70B9`, reached from `000E:7439` (the
  top-level screens). So the main stream is seeded from the hour and minute at launch, and possibly
  again later in a session, when that byte is 2 or 5.
- A second stream: `0791:94C9` calls `214B:0688` with the seed at `DS:8336`; `0791:F3F2` (the start-up
  of unit `0791`) stores the BIOS tick count (linear address 0x46C) there. `0791:94C9`'s only caller is
  `0791:94E8`.
- `214B:1DA7` counts loop iterations between two BIOS ticks: a delay calibration, at start-up.
  `214B:0D90` reads the tick count while it waits for a key.
- `1771:97CC` (creates the 20 players of a country) and `0791:15B9`, `0791:2648`, `0791:0C65` read the
  pointer at `DS:A978` directly.
- Both seeds are in guest memory, so a savestate holds them. F001's different quick results from
  one savestate (D3, batches a and b) are therefore not explained by the seeding alone.
