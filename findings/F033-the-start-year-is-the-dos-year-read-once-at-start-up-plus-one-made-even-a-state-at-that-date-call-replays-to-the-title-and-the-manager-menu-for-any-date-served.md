# F033 The start year is the DOS year read once at start-up, plus one, made even; a state stopped at that date call replays the title and the new game for the date the core serves

- **Status**: proposed
- **Question**: #369 (T83, a request from goal2, follow-up to #367 / F032): where the original reads the DOS date from program start to the title's key read, where it stores it, how the start year and opening stage follow, which years are accepted, what else depends on the date; a state goal2's core can resume before that read; every interrupt from there to the title's read, shown complete by two dates against DOSBox-X
- **Tests claims**: none (no `spec/` row); bears on F004 (the DOS year as a second input), F023 §9 and F025 §2 (the opening stage by year: goal2's NG-6), F032 (the path after the title)
- **Experiment and runs**: E039, `experiments/E039-start-year/` (`run.py`, `derive.py`, `trace.py`, `summarise.py`, `out/`); E039-r0001 (DOS date 10/04/1990) and E039-r0002 (10/04/1992), each a new game to the first manager menu; E039-r0003 … r0005, attempts to catch a state during start-up (`--catch-only`), r0005 keeping one; the derivation `out/derive-r0005.json` and the traces `out/trace-1990.json`, `out/trace-1992.json` (the original's code under Unicorn: no record, a static method)
- **Artifact**: set `goal2-67cf27d6` (the runs); the listing of set `goal2-a949da2f` (`static/goal-exe/README.md`)
- **Max intervention**: I3 (DOS date and time set in the autoexec, read back; savestates written, I2; memory, registers and screens read, I1)
- **Tier reached**: V2 for the dates run (1990, 1992): listing, DOSBox-X runs and a Unicorn run of the original's code that reach the same states; other years from the listing only
- **Confidence**: unreviewed. Words as `docs/wide-pass.md`: **read**, **measured**, **likely**.

## Answer

- **One date read, at start-up** (read; measured): from program start to the title's read, the program reads the date once: unit start-up `214B:206A` (the third unit initialisation, called at `0000:000A`) ends with `call 0x1c63` at `214B:2108`, and `214B:1C63` calls `GetDate` `235C:006C` at `214B:1C7D`, which executes `mov ah, 2Ah; int 21h` at `235C:006F`/`0071`. It is an `int` instruction (not `Intr`). The year (CX) is stored at **`DS:A9FD`**; month, day and weekday go to three locals of `214B:1C63` and are dropped. No other call of `235C:006C` exists, and `GetTime` `235C:00A2` is never called (F004). In both traces the only INT 21h AH=2Ah of the whole path to the first manager menu is this one. static:static/goal-exe/code/seg_214B_04.asm:443 static:static/goal-exe/code/seg_214B_03.asm:1084 static:static/goal-exe/code/seg_235C_01.asm:99 (E039-r0001, E039-r0002)
- **The start year and the stage** (read; measured): `DS:A9FD` is read once, by `init_new_game` `1771:9B85`, which the main program calls at `0000:0035`, after the title returns (after `n`, the player count and the GOAL.DAT load): start year `[DS:A923]+0x3A` = `DS:A9FD` + 1, then + 1 more if odd (`9B98`–`9BB1`); `+0x38` = 0; `+0x40` = 1 if start year mod 4 = 2 else 0 (`9BC5`–`9BDB`); stage `+0x3C` = `DS:118E[+0x40]`, and `DS:118E` holds `02 05` (`9BE9`–`9BF0`): **stage 2 when the start year is divisible by 4, stage 5 when it is 2 mod 4** (goal2's NG-6). The start year is always even. Measured: DOS 1990 → `+0x3A` = 1992, stage 2, `+0x40` = 0 (E039-r0001); DOS 1992 → 1994, stage 5, `+0x40` = 1 (E039-r0002); DOS 2026 → 2028 (E038-r0001: the "2028" of the screens). static:static/goal-exe/code/seg_1771_14.asm:394 static:static/goal-exe/code/seg_1771_14.asm:427 (E039-r0001, E039-r0002)
- **Accepted years** (read): the program checks nothing: any CX is stored and used (a word; `inc`, the parity fix). What limits the year is DOS: INT 21h AH=2Bh (set date) and DOSBox-X's `DATE` accept 1980–2099 (the driver refuses others, `driver.clock_values`), so a real PC gives start years 1982–2100. A year before 1980 or after 2099 is not one DOS can return; what the game does with it (screens, the calendar) was not tried. (E039-r0001)
- **What else depends on the date** (read; measured): on the path to the first manager menu, nothing but the start year and stage: the seed is the DOS time read later (F032, `23E4:11D9`); no file is written (save names are not on the path); the calendar is built from `+0x3A`/`+0x3C` by the new-game code after the title. DOS keeps its own copy of the date in guest memory (in this DOSBox-X: the year word at linear `07C7A`, the weekday at `07C76`); GOAL never reads it (it asks INT 21h); a core that answers AH=2Ah itself leaves that copy as its state holds it (1990 in the delivered state), which matters only to DOS functions that stamp files, and the core serves those itself. (E039-r0001, E039-r0002)
- **No key read comes before the date read** (read): the first key read is the title's (`1771:085A`), after `214B:206A` returns; so the state is one stopped **at the date call**. DOSBox-X 2024.03.01 here has no debugger, so it was made in two steps: E039-r0005 caught a savestate during start-up (CPU load+2382:0074, the CRT unit's start-up, `DS:A9FD` still 0), and `derive.py` ran the original's code under Unicorn from it to `235C:0071` and wrote that state (E039-r0005).
- **The state for goal2's core** (measured): on the owner's Drive, folder root, `e039-r0005-date-call.sav`, sha256 `0d9c683023c7327f17bfc29900f2eff4e703641d21d3f353693f09654688494b` (`out/derive-r0005.json`; also under `goal2-archaeology/E039/` as `e039-date-call-r0005.sav`, with the run's states). Its CPU: **CS:IP = load+235C:0071** (2B7F:0071 at load 0823), the `int 21h` not yet executed, **AX = 2A10** (AH = 2Ah), BX = 3D6F, CX = 0000, DX = 296E, SI = 0000, DI = 3DF0, BP = SP = 3DDA, SS = 3875, DS = 2DA4 (the data segment), ES = 3D6F, FLAGS = 7206. On the stack from SS:SP: the saved BP `3DF6`, the far return `214B:1C82` (`1C82`, `296E`), then GetDate's four far pointers (the locals of `214B:1C63` and `DS:A9FD`). "Resume at a DOS call": serve the `int 21h` as DOS does (CX = year, DH = month, DL = day, AL = weekday, 0 = Sunday), set IP to `0073`, and run. `DS:A9FD` = 0, `DS:A9FF` = 4279 (the delay calibration, done), the BIOS tick 0040:006C = 655438. The source state (CPU load+2382:0074) is `e039-r0005-pre-date.sav`, sha256 `0dc34463…` in E039-r0005. The written file is the caught savestate with its `Memory` component and the `CPU` component's registers replaced (`derive.py`); it is a state for goal2's core, not one DOSBox-X was shown to load. (E039-r0005)
- **The interrupts from the date call to the title's read** (measured; read), in NG-7's form:

| # | when | interrupt | site | callers | the core answers |
| --- | --- | --- | --- | --- | --- |
| 1 | the state's first instruction | INT 21h AH=2Ah (get date), the `int` at `235C:0071` | `235C:006C` `GetDate` | `214B:1C82` (in `214B:1C63`), `214B:210B` (near, in `214B:206A`), `0000:000F` | CX = year, DH = month, DL = day, AL = weekday; the year goes to `DS:A9FD` (E039-r0001) |

  and nothing else. Between it and the title's read the program runs the remaining start-up (`2139:0000`, `2138:0000`: heap allocations), `0791:F3F2` (it stores the BIOS tick count's low word, a memory read, at `DS:8336`, the second random stream, F004), and the title: its drawing, 333 "key pressed?" polls (`214B:0723`, returns `1771:0723` ×216 and `1771:0782` ×117, the animation's 9 × 37 cells, answered "no key") and the speaker by port I/O (OUT 43h ×1, OUT 42h ×666, IN/OUT 61h ×2 each; no interrupt). The core needs no INT 10h, no timer, no file here. After the title's read the path is F032's (GOAL.DAT, the DOS time), unchanged by the date. (E039-r0001, E039-r0002)
- **Complete for these dates** (measured): from the one state, served DOS date 10/04/1990 and 10/04/1992 (and the time each record shows DOS answered), the traces reach every read of E038's path at the same site, with the same callers, the same screen text, the same `DS:A9FD`, `DS:7B62`, `DS:7B64` and game-record `+0x38..+0x41` as the DOSBox-X record of that date (`summarise.py`: 6 of 6 reads, both dates); at the first manager menu the screen's 4000 bytes, the player and country arrays are byte-equal, and of conventional memory only these differ: `DS:A9FF` (4279 against DOSBox-X's 4275: the calibration ran under the modelled tick), the BIOS keyboard buffer and tick count, DOS's PSP word (`0813:002E`), dead stack below SP, and, for 1992 only, DOS's own date copy (linear `07C76`, `07C7A`, above). `DS:8336` is `004E` in both runs and both traces. (E039-r0001, E039-r0002)

## Method

- F025 (its "Start stage", C-COMP-02) read `1771:9B85` the same way; F033 adds where `DS:A9FD` comes from and measures it.
- Static first (rule 22): every call of `GetDate`/`GetTime` and every `int 21h` with AH=2Ah (`static/goal-exe/code/`, `calls.tsv`), the readers of `DS:A9FD` (`datarefs.tsv`: `214B:1C63` writes, `1771:9B85` reads), `1771:9B85` itself, the main program `0000:0000`. The listing settles items 1 and the stage; runs were needed for the state (no key read precedes the date read, item 2) and to show the served list complete (item 3, asked for by goal2).
- DOSBox-X runs (`run.py` at each record's `code_commit`): `cycles=30000` fixed, DOS time 10:00:00, DOS dates 10/04/1990 and 10/04/1992; E038's keys and kept states. The catch: savestates polled from 0.2–0.4 s after the window appears (`--first-save`), the first with the CPU in GOAL.EXE's code (load + 0000..2580) and `DS:A9FD` = 0 kept; the start-up before the date read is shorter than one poll interval (0.58 s), so most launches miss it (r0001 … r0004; two earlier catches wrote no record and are not used: README amendments 1–2).
- `derive.py`: from E039-r0005's state to `235C:0071` under Unicorn, the BIOS tick advanced every 1,647,750 instructions (30000 × 54.925 ms: what `cycles=30000` means for DOSBox-X) for the calibration `214B:1DA7` that start-up runs, 3 ticks served; the interrupts on the way served as DOS and the BIOS do: INT 21h AH=25h at `2382:0095` (the CRT unit sets vector 1Bh) and INT 10h AH=02h twice through `Intr` (`214B:0661`, cursor to row 1Ah, column 1); the text page is not written. Log `out/derive-r0005.json`. (E039-r0005)
- `trace.py`: E038's trace from the derived state, the date answered as DOS does, the time as the record of that date shows DOS answered (`DS:7B64`: 10:00:59.89 for 1990, 10:00:59.78 for 1992), E038's keys and the name entry's poll; any interrupt it does not serve stops it (none did). `summarise.py` and E038's `compare` against the record's states.

## Observations

- E039-r0001 and E039-r0002: the title's read with the CPU at F000:CFAA/CFB2 and E038's callers; `DS:A9FD` 07C6 / 07C8 from the title on; the game record `0000 c807 02 01 02 01 00 01` / `0000 ca07 05 01 02 01 01 01` from country selection on; `DS:A9FF` 4275 in both. (E039-r0001, E039-r0002)
- E039-r0005: caught at the second savestate (CPU 2BA5:0074 = load+2382:0074). (E039-r0005)

## Inferences

- **What goal2's core needs for a chosen start year** (likely, from the Answer; E039-r0001, E039-r0002): a second entry kind, "at a DOS call": load `e039-r0005-date-call.sav`, answer its first instruction (INT 21h AH=2Ah) with the player's date, then run as from the title state, serving polls with "no key" through the title's animation; the DOS year Y gives the start year Y + 1 rounded up to even, so a player wanting start year S (even) answers Y = S − 1 or S − 2. The tick count stays as the state holds it (`DS:8336` then `004E`); a core that wants `DS:8336` to vary must advance 0040:006C itself. (E039-r0001, E039-r0002)

## What this does not establish

- Years other than 1990 and 1992 (2026 by E038), and any year DOS cannot return: from the listing only.
- That DOSBox-X loads the derived file (not tried); the core reads only `CPU`, `Memory` and the text page.
- The state's `DS:A9FF` is the modelled tick's, not one DOSBox-X produced (4279 against 4275).
