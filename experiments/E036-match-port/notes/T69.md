## How the ports are written

- A port keeps the original's frame: `mem.enter` builds `push bp; mov bp, sp; sub sp, n`, and every local the listing writes is
  written (the nested procedures 1C78, 1E53, 2218 read their parent's frame; the families' memory digests include the
  dead stack, which DS holds). A call of a routine that is still the original's is a guest call (`go`) with the listing's
  arguments and return address, so the stack of every callee is the original's; a ported callee runs as its port inside it.
- The SITES table lists each of the 86 calls (the instruction's offset, the callee, near or far, the return address, the
  words the callee pops). `tests.test_port_frame.ListingTests` checks every row against `static/goal-exe/code/`: that the
  instruction is that call, its length, `push cs` before a near call that returns far, the callee's `ret n`; and that no call of
  the 14 routines lacks a row. (The table was generated from the listing first, so this test passed at once; the tests of the routines found
  the one error, 998C below.)
- AX and DX are left as the listing leaves them where a callee or the proof could read them: after a call they are the
  callee's; the small functions (1C78, 1E53, 1D4A, 970C) set both; a word pushed from AL carries the AH the listing had (the
  products of `mul`, `cwde`).
- `998C` pushes the first `2996` result, which stays on the stack under 6B65's call and is popped by 1EB5's `ret 8`. The
  guest-call mechanism (T59) knows a callee that pops fewer words than were pushed, not more, so the port pushes the word by
  hand for 6B65's call (its frame is one word lower, as the original's) and takes it back before 1EB5's call, which pushes it
  again at the same address (the first run of the first version stopped there: the frame never resumed, T59's `returned()`
  waits for the SP the call left).
