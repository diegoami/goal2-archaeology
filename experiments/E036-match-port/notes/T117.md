## Receipts (`out/T117/`, producer `drive_receipt_v1.py`)

Each was run from a pristine clone at the named head, so no edit could reach a running receipt.
`before` is `1bc7720e` (main's port runtime plus the producer); round 2 is `6d23db28`, round 3
is `eb2b1046`; each receipt records its `head`.

- `taps-*`: E034-03's straight drive with every io_tap, write_tap, site and listener call hashed
  in order. `taps-before-v1` and `taps-after-r3` ran without a fixed `PYTHONHASHSEED`: their events,
  result, memory and every tap count are equal, their tap hashes differ. `Regs.store()` sets the
  dirty registers in a set's order, and string hashing is randomised per process, so the order of
  those `set_reg` taps can change between any two runs of the same code. With
  `PYTHONHASHSEED=0` for all three, `taps-before-seed0-a` and `-b` agree with each other
  (determinism control) and `taps-after-r3-seed0` equals them: the same 158,092,779 io calls,
  114,492 listener and 81,134 site calls, in the same order with the same values.
- `cpu-*-dev2`: the untapped drive at the round 2 head, before and after run at the same time
  under one load: 251.4 s to 180.7 s CPU for the drive, 44.4 s to 35.5 s for the shootout stretch;
  events, result, memory and stretch count equal. Development measurements, not Done-when 2's.

The untapped fast paths are taken only with no io_tap, so the tap receipts check the tapped
path and the cpu receipts' equal events, result and memory check the fast one.

The guard measures wall-clock time, so load trips it too: under heavier local load both the
unchanged code and round 3 exceeded 60 s on the shootout stretch.
